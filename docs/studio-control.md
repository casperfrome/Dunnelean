# 工作台可靠控制协议

除运行 ID 接口外，服务提供面向协调器的 request ID 接口。工作台使用稳定的本地运行 ID 作为 `request_id`；重新执行业务任务必须使用新 ID。

`GET /healthz` 返回 `state_store_id`。它在 SQLite 状态库首次打开时生成，重启保持不变。协调器将其与本地运行一起持久保存，随后在请求中发送 `x-dunnelean-state-store-id`。如果身份不一致，服务返回 HTTP 409 / `STATE_STORE_CHANGED`，不会继续提交或取消操作。

| 接口 | 行为 |
| --- | --- |
| `GET /v1/requests/{request_id}` | 返回 `{request_id,cancel_requested,run}`；运行和取消记录都不存在时返回 404 |
| `POST /v1/requests/{request_id}/cancel` | 持久保存取消记录，取消活动运行并返回上述信封；`run` 可以为空 |
| `POST /v1/runs` | 同 ID/同配置返回原运行；不同配置冲突；首次提交遇到取消记录时返回 409 / `REQUEST_CANCELLED` |

取消记录与运行状态修改在 SQLite 事务中完成，进程重启后仍有效。提交记录与注册取消令牌使用同一活动任务锁，与取消路径锁顺序一致，避免提交已落库但令牌尚未注册时丢失取消。

提交响应丢失时，可查询 request ID；如果确认同一状态库不存在该请求，使用完全相同的配置和 request ID 再次提交。停止应调用 request ID 接口：先到达的取消会拒绝迟到的提交。取消后可保留原运行的终态供审计，不能把确认取消视为回滚已提交批次。

协调器重启应核实并停止旧任务，不自动恢复数据传输。状态库身份变更、失联、缺失记录或 `commit_unknown=true` 时，不能假设目标可重新写入。工作台需保留目标锁，检查数据库在途操作与批次凭据，再人工决定后续处理。

取消记录不自动过期，因此状态数据库需要持久备份。该协议面向本机可信调用者，服务监听地址应保持 loopback。
